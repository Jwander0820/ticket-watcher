# 維運與疑難排解

[文件索引](README.md) · [CLI 使用](cli.md) · [部署與備份](vps-migration.md)

## 先看狀態與健康

對正在執行的服務使用相同設定：

```sh
ticket-watcher --config config.yaml health --json
ticket-watcher --config config.yaml status --json
ticket-watcher --config config.yaml events --detail full --json
```

Docker 請在相應容器中執行，命令見 [CLI 指南](cli.md#檢查與常駐)。UI 也提供票況、最近事件、查詢紀錄與工作恢復狀態。

`health` 使用 SQLite 唯讀連線，不建立 Watcher、HTTP client、資料庫或執行 schema 遷移。`run`／`tick` 執行期間每 30 秒獨立更新 heartbeat，長查詢與通知等待不會阻止更新；距離上次 heartbeat 不到 120 秒才視為程序健康。

健康資訊包含各目標最近成功查詢、最後錯誤、平台暫停與待送通知數。**程序健康不代表票網可查或 Discord 已送達**；平台限制不會直接讓 heartbeat 失敗。資料庫不存在、版本不支援或 heartbeat 過期時，`health` 回傳非零退出碼。

## 常見狀況

| 狀況 | 檢查與處理 |
| --- | --- |
| 新增後沒有查票 | 確認目標已啟用、停止時間未到，查看下一次排程；新 UI 目標預設停用 |
| 第一次就有票，但沒有通知 | 首次只建立基準；後續由無票轉有票才建立 `RELEASE` |
| 按「查詢一次」仍延後 | 查看 `reason`、`next_allowed_at`、平台／目標暫停與退避；立即檢測只略過例行排程 |
| `QUERY_SUPERSEDED` | 舊查詢租約已失效或被接手，結果不會覆寫新基準；讓現有工作依排程繼續 |
| 有票況卻沒有最近成功時間 | 檢查 `complete`、UNKNOWN 與最後錯誤；不完整結果不等於完整成功 |
| 通知持續 `PENDING` | 確認目標選擇的頻道有 Webhook、等待期限與 TTL；未配置 Webhook 不消耗送信次數 |
| UI 測試有收到，監控通知沒收到 | 測試只驗證頻道；再看是否真的有釋票事件，以及通知是否取消或過期 |
| CLI 讀不到 UI 的目標或票況 | 使用 UI 的設定檔，Docker 使用 UI 容器內 CLI；勿另讀宿主機獨立 DB |
| 改了 YAML 卻未生效 | CLI 常駐與外部手動修改的 UI 設定需重啟；UI 表單儲存會自動重載 |
| 活動改期後仍顯示已停止 | 依 [自動停止說明](configuration.md#演出開始後自動停止) 更新期限與來源時間 |
| `health` 失敗 | 確認設定與 DB 路徑正確、服務已啟動；未啟動常駐服務時不會持續更新 heartbeat |

## 限流、退避與暫停

429 保存平台共用等待期限，使用伺服器 `Retry-After` 與本機退避較晚者。401／403／驗證頁會暫停平台；連續三次解析異常會暫停目標。失敗或缺少資料不是售完，不能用另一個出口繼續查。

### 原因未明的 403：一次自動恢復試查

監控的自動／手動檢查收到 HTTP 403，且完整讀取的診斷沒有 CAPTCHA、Cloudflare／AWS 驗證、地區限制或明確限流特徵時，會保存一個隨機 **12～24 小時**後的試查時間。等待期間平台仍為 `BLOCKED`，其他查票操作不能放行。`Retry-After`、平台冷卻與請求間隔、目標退避仍取較晚期限；服務暫停或排程的暫停時段可使實際試查晚於 24 小時。

到期後只對原目標、原來源與原代理設定執行**一次完整票況查詢**。這是一次查詢機會，不是固定一個 HTTP 請求：快取有效時通常只需一筆動態請求，元資料過期時會包含原有的靜態資料請求；不額外重試或改出口。

- 完整成功：票況與解除平台暫停一起寫入資料庫，保留原有票況比較／釋票通知；其他逾期監控依既有 60～90 秒錯開規則恢復。
- 再次拒絕、網路／解析錯誤、資料不完整或工作中斷：維持平台暫停，保存自動恢復失敗事件，不再安排第二次試查。Discord 告警沿用「通知查詢異常與恢復狀態」開關與目標頻道。
- 試查機會在發送請求前持久化消耗；程序重啟不重新抽時間，也不重播結果不明的試查。若程序意外終止，租約到期後由監控工作記錄失敗並安排告警。
- 原目標被停用、刪除、改變來源／篩選、到期、另行暫停，或代理設定改變時，取消自動恢復並維持平台暫停。服務整體暫停只延後試查，不消耗機會。
- 401、明確驗證頁、診斷未讀完整、單次 `query`／更新基本資料所觸發的阻擋，以及升級前已存在但沒有恢復計畫的暫停，仍需人工處理；不根據舊日誌自動解除。

`status` 的 `platform.recovery`、`health` 的 `platform_recovery` 與控制台提供 `WAITING`／`PROBING`／`FAILED`、預定時間與結果。實際試查另寫一筆 `mode: recovery` 查詢紀錄。人工解除平台暫停會取消尚未執行的計畫；試查進行中需先等待結果。

需要人工處理時，先確認存取或來源問題已處理，再解除對應範圍的暫停：

```sh
ticket-watcher --config config.yaml resume --platform ticketplus --json
ticket-watcher --config config.yaml resume --target my-event --json
```

`resume` 不清除伺服器等待期限，尚未到期的排程保持不變。實際解除暫停時，既有且已逾期的目標會隨機排列，從平台等待期限之後每隔 60～90 秒安排一筆補查；重複解除不會再次延後。常駐程序啟動／重啟或 UI 恢復運作也使用相同規則，詳見 [控制台暫停與恢復](ui.md#暫停運作保留-ui)。同程序操作會立即喚醒排程以等待新期限；其他 CLI 程序修改共享 DB 後，常駐程序會在下一次 30 秒 heartbeat 檢查到變更。

## 通知狀態

事件建立與送達是分開的結果。可查看 `PENDING`、`INFLIGHT`、`SENT`、`CANCELLED`、`EXPIRED`、`FAILED` 或 `DISABLED`；只有 `SENT` 加上 `message_id` 代表 Discord 確認送達。

票況通知按同一輪、同一場次合併。觸發時列出監控範圍內當輪所有有票／暫無票券的票區或票種，包含狀態未變的項目；售完或無法確認的項目不列入。有票排前面並逐項顯示餘票，暫無票券排後面；至少一項可購買時標題為「🟢 有票」，只有暫無票券時為「🟡 暫無票券」。每則只保留活動與場次時間、各區票況、偵測時間和一個購票連結，並關閉 Discord 自動產生的連結預覽卡片；購票連結仍可點擊。來源未提供精確數量時保留來源票況，不推算張數。

不同場次分則通知，過長的同場次清單按完整項目分則接續，各則、各頻道分別保存送達與重試紀錄。通知仍只由原有狀態轉換觸發，首次觀測及相同狀態不會反覆發送。事件完整內容保存觸發變更與當輪清單，摘要不展開清單。系統通知縮為狀態與簡短說明；查詢異常／恢復使用該監控勾選的頻道，服務中止／恢復使用「輪詢設定 → 監控服務異常通知」勾選的頻道。

預設 TTL 為 10 分鐘；到期不補發。更換頻道、停用目標、改變來源／篩選、票況已不可購買或場次開始，都可能取消或縮減待送通知。釋票線索消失後不再送出舊線索；後續確認有票可另建立 `RELEASE`。

送信重試使用穩定事件 ID，禁止 mentions；已取消或由其他程序接手的通知不會被舊回應恢復。事件 ID 保留在控制台及 API，不顯示於通知正文。Discord 已收到請求但成功回應遺失時，重試仍可能重複。已發出的 HTTP 請求無法撤回。

## 監控工作恢復

UI 監控工作若發生未預期例外、意外返回或被取消，依序等待 5、15、30、60 秒，之後每 300 秒重建監控工作與 HTTP／SQLite 連線。替換前先結束舊工作，保留票況基準、通知佇列、排程、限流與平台／目標暫停。

同一次持續故障只建立一則異常事件，重啟後持續運作 60 秒才建立恢復事件。正常關閉或儲存設定不算故障。通知設定見 [控制台指南](ui.md#監控服務異常通知)；Discord 連線失敗不會阻止工作重試，變更告警目的地或關閉通知時，舊待送告警會在送出前取消。

CLI `run` 遇到非預期錯誤會退出，由 Compose 的 `restart: unless-stopped` 恢復。UI 的程序內恢復與 Discord 告警都無法保證在主機離線、程序被強制終止或資料庫不可寫時即時送達；主機離線需外部監測。重啟本身不解除平台暫停；符合上述 403 條件時，僅由到期的單次試查決定是否恢復。

設定儲存後若新監控暫時建立失敗，UI 仍可讀取設定與恢復狀態，並使用相同重試流程。手動查詢與測試通知不鎖住狀態讀取；重載或替換工作前會取消並等待這些操作結束。

設定寫入失敗時會恢復原本的私密設定內容與檔案有無，避免假的版本衝突。若回復也暫時失敗，程序在背景重試，完成回復後才重啟監控與通知；回復期間暫不接受新設定儲存。可先檢查資料目錄權限及可用空間，避免再啟動另一個監控程序。

控制台 API 遇到未預期例外（例如 SQLite 暫時鎖定）時，回傳一般 JSON 錯誤與相同的安全標頭，不回顯例外原文；Docker 日誌只記錄 `ui_request_failed`、HTTP 方法、路徑與例外類型，不含訊息或 traceback。單次請求失敗不會中止監控工作。網頁連不上服務，或收到代理錯誤頁、登入頁等非 JSON 回應時，也會顯示可讀的說明，而不是解析錯誤。

## 查詢紀錄與保留

| 資料 | 位置與保留方式 |
| --- | --- |
| 查詢紀錄 | DB 旁 `<資料庫名稱去除副檔名>-logs/queries.log` 與 `queries.previous.log`；每 7 天輪替，保留目前與上一週期，最長 14 天 |
| 票況事件與通知紀錄 | SQLite；歷史預設保留 30 天，未完成工作另行保留，通知仍依自己的 TTL 過期 |
| Docker 程序日誌 | Docker `json-file`；每份 5 MB，最多 3 份 |

UI 的「查詢紀錄」顯示最近 100 筆檢測，包含時間、目標 ID、手動／自動、成功／不完整／失敗、票況摘要、請求數、耗時及下次排程。單次 `query` 也會留下紀錄；明確手動操作未能執行時記錄原因，自動等待排程不寫紀錄。功能啟用前的歷史不會補造。

每行一筆 JSON，只保存摘要與目標 ID，不保存 Webhook、完整 URL、頻道名稱、HTTP 原始回應或例外原文。Docker UI 預設目錄為 `/app/data/watcher-logs/`。檔案寫入失敗會在 UI 顯示原因，監控本身繼續運作。

HTTP 401／403 會附上 `http_diagnostic`，也寫入 Docker 日誌的 `source_http_diagnostic`。可從上述日誌檔、查詢結果 JSON 或控制台的 `/api/state?view=logs` 讀取，無須重新查票。內容包含：

- HTTP 狀態／版本、`get` 或 `getS3`、靜態資源種類、此輪第幾次請求及本次 ID 數量（不保存 ID 值）。
- `direct`／`configured_proxy` 路由設定及 User-Agent；不記錄代理網址、帳密或另行查詢出口 IP。
- 白名單化的 Server、Content-Type、Content-Encoding、X-Cache、`CF-Mitigated: challenge`、Retry-After 秒數，以及格式有效的 CloudFront／Cloudflare／AWS 追蹤 ID。
- 錯誤頁只在記憶體中讀取最多 16 KiB（壓縮前後皆有限制）、最多 1 秒且受整體請求逾時限制；只保存已知特徵，例如 `cloudfront`、`request_blocked`、`cloudflare_challenge`、`access_denied`，不保存原始文字、Cookie、Location 或任意標頭。無已知特徵時保留空清單，不猜測原因。

診斷只讀取已發出的那一次回應，不增加即時探測或重試。錯誤頁過大、壓縮異常、逾時或讀取失敗，仍維持人工處理的 `BLOCKED`；診斷期間取消工作也會保存平台暫停。403 的 `Retry-After` 本身不構成自動恢復資格；符合上述條件時，保存的等待秒數會限制試查最早時間。追蹤 ID 可協助平台方比對日誌，但回應特徵本身無法證明是哪條 WAF 規則、IP 封鎖或解封時間。

明確驗證標頭優先於一般 HTTP 狀態判定：Cloudflare 的 `CF-Mitigated: challenge`、AWS 的 `x-amzn-waf-action: captcha`／`challenge` 都維持人工處理，包括 AWS 使用的 202／405 回應。[AWS 官方行為說明](https://docs.aws.amazon.com/waf/latest/developerguide/waf-captcha-and-challenge-actions.html)

輪替以第一次建立週期起算，期限與進度寫入 SQLite，重啟不重算；常駐服務即使沒有新查詢也會清理舊週期，停機期間則在下次啟動／讀取時清理。輪替、追加或讀取中斷可接續重試，不會因重複輪替提早刪除上一週紀錄。

歷史清理每小時最多執行一次，日誌依保存期限維護；暫時 I/O 維護錯誤才每 30 秒重試。通知過期由佇列即時檢查，不會延後到下一次歷史清理。備份應包含整份資料目錄，見 [部署與搬移](vps-migration.md)。
