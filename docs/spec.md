# 規格依據與第一版實作

本專案依引用對話「命名 GitHub 儲存庫」中的完整 v0.1 規格，以及 v0.1.1、v0.1.2 的對話補充實作。對話內 `sandbox:/mnt/data/` 下載附件未能從此工作區取回，因此本文件是實作整理，**不是下載附件的逐字副本**。

核心需求：低資源、後期蹲釋票、一般隨機 300～900 秒、釋票後 60～180 秒、單一穩定出口；Python 核心供 CLI、VPS、外部排程與 AI 共用，MCP 可日後另做薄包裝。

| 模組 | 第一版實作 |
| --- | --- |
| 資料來源 | 已驗證公開 HTTP API，支援場次粒度，公開與內部 ID 轉換 |
| 單次操作 | capabilities、query、status、events、check、tick、health、resume |
| 常駐 | run；共用 HTTP client；本機每 5 秒檢查排程，未到期不查網站 |
| 狀態 | UNKNOWN／UPCOMING／AVAILABLE／SOLD_OUT／PAUSED／ENDED；本次觀測與最後有效值分開 |
| 釋票 | 同一穩定項目的最後有效 SOLD_OUT → AVAILABLE；首次有票不報；同輪合併通知 |
| 快速模式 | 30 分鐘；再釋票延長；持續有票不延長；兩次完整無票退出 |
| SQLite | 票況、排程、事件、outbox、平台節流與租約；UTC 時間；重啟恢復 |
| 異常 | 網路 15／30／60 分鐘退避，429 平台共用等待，403 暫停，解析三次暫停 |
| Discord | 環境變數 webhook、wait=true、訊息 ID、禁用 mentions、獨立重試、TTL 10 分鐘 |
| 保留與健康 | 30 天事件歷史，保留未完成工作；heartbeat 與觀測能力分開 |
| 部署 | Docker Compose、named volume、非 root、唯讀設定、無入站 port、日誌輪替 |
| AI 使用 | JSON 摘要／分頁、query 無比較、CACHE 原始時間、PENDING 與 SENT 分開 |

`query` 不建立事件、不發通知、不覆蓋監控基準，但會保存共用平台限流與元資料快取。查詢取得有票只能稱當下可購票，不能宣稱剛釋票。status／events 不查外部網站。

v0.1.0 當時的限制：票區與逐席資料、價格篩選、MCP、Discord Bot、多平台、Web UI 尚未實作；後續票區補充見下節。不加瀏覽器 fallback 或自動 IP 輪換。Docker 部署檔案已提供，不代表已在 VPS 部署或驗證實際 Discord 送達。

## v0.1.1 案例補充

依使用者提供的 YUURI 外頁、女巫店販售中內頁與手動刷票經驗，補入 `order` URL 的 AREA／PRODUCT 粒度。活動外頁仍採 SESSION，完整查詢會提供每場的 `order_url`。只有外頁也能取得售完場次的公開票區資料；使用內頁網址設定獨立目標即可。

新增外頁 `TEMPORARILY_UNAVAILABLE`，對應「暫無票券」。最後有效 `SOLD_OUT → TEMPORARILY_UNAVAILABLE` 只建立 `RELEASE_HINT` 與線索通知，`evaluation.release_detected` 仍為 false；再次相同狀態不重複通知。從 `SOLD_OUT` 或 `TEMPORARILY_UNAVAILABLE` 轉為 `AVAILABLE` 才建立 `RELEASE`。首次快照仍不報釋票或線索。內頁 unavailable 為無票，不套用外頁線索規則。

票區與票種的動態 API 依同一租約／節流取得完整資料，再比較、篩選與分頁；多於 100 個分批查詢，最多 1000 個。內頁訊息含場次、票區／票種名稱、來源價格及頁面顯示的餘票訊號，未提供的逐席位置不推論。remaining_count 僅暴露網站「剩餘 N」對應的 0～20；熱賣中的數量為 null。

兩種事件各自有待送佇列、取消和去重。線索消失時取消過期前尚未送出的線索，後續確認有票再建立確認事件。線索也觸發原快速模式，完整確認無票兩次仍退出。SESSION 來源升為 v2，已有 v1 來源在下次成功查詢時重新建立基準，不跨語意判定釋票。

原一般 300～900 秒、快速 60～180 秒與請求至少隔 5 秒保持不變；使用者提供的 1～3 秒手動刷新經驗沒有當成自動改頻率的要求。票區支援已完成，逐席位置、價格篩選、MCP 等仍未實作。

資料來源和設定基準改變時重新建立初始狀態。單次 query 與常駐程序必須使用同一 DB 才能共用限流。跨網路主機不自動同步 SQLite。

通知更新與事件入列使用同一 SQLite transaction。跨系統發送只能盡量去重：Discord 收到後若成功回應遺失，重試仍可能重複；訊息中保留穩定事件 ID。後續已確認不可購買的待送項目會取消或從訊息中移除，過期通知不補發。

## 2026-10-06 審閱修正

- 通知結果依領取識別、嘗試次數及有效租約條件回寫，已取消事件與後續接手的嘗試不受舊回應覆蓋。新通知記錄目標設定簽章；舊版待送事件仍相容。不可購買項目的排除也涵蓋送信中的事件，防止失敗重試時重新出現。
- `run` 分開執行查票、通知與 heartbeat；`tick` 通知與查票並行，等待最後通知批次後返回。單次 `check` 仍嘗試立即通知。送信使用整體逾時，租約長度涵蓋該逾時。
- Heartbeat 每 30 秒更新，完整成功的單次 `query` 重設平台失敗累計；原有伺服器等待期限、監控基準與查票間隔保持原義。
- 歷史清理的執行時間寫入共用資料庫，每小時最多一次；停用目標只檢查尚未完成的通知。`status` 在 SQL 層統計摘要及分頁讀取明細。

## 2026-10-06 本機控制台

新增 `ui` 指令與 `compose.ui.yaml`。控制台包含常駐監控、目標新增／編輯／停用、每目標指定一個 Discord 頻道、輪詢設定、最近 20 筆事件及明確操作的測試通知。表單儲存後重新載入設定；保留原有輪詢下限、平台等待期限與未改來源的觀測基準。

命名頻道的 Webhook 存在資料庫旁的私有 JSON 檔案，不寫入 YAML、SQLite 或 API 回應；既有環境變數預設頻道保持相容。通知建立時固定頻道，更換目標頻道後取消尚未送出的舊通知。控制台限本機使用，包含 Host／Origin 驗證、CSRF 與設定版本衝突檢查；尚未提供遠端登入或多人管理。
